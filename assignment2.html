06

Split Unit Used to Prevent Leakage

Proposed split unit: a group of duplicate or potentially near-duplicate images. All retained images in a group go into the same set: train, validation, or test. An image with no detected matches forms its own group.
  1. Check exact copiesKeep one copy when identical images share a label. Exclude identical images with conflicting labels pending manual review.
  2. Keep similar images togetherThe provisional split keeps automatically flagged near-duplicate candidates in the same set. Review these candidates and source identities before finalizing the split.
  3. Prevent overlapThis reduces the chance that the model is evaluated on a copy of a training image. Apply augmentation and fit dataset-derived normalization statistics using training data only.
07

Evaluation Metrics

Primary metricMacro-F1

Calculate F1 for each food class, then average across all 30 classes. Each class has equal weight, including those with fewer images.

Additional metricsAccuracy and per-class scores

Accuracy measures the proportion of correctly classified images. Precision, recall, and F1 are also reported for each food class.

Error analysisConfusion matrix

A 30 × 30 matrix shows the true and predicted food classes, revealing which dishes the model commonly confuses.

Select the model checkpoint using the highest validation Macro-F1. After model selection is complete, report all metrics on the held-out test set.

Dataset Audit

Every image of Kaggle version 11 was decoded and checked. The class label is the name of the image's folder. The original Kaggle Train / Validate / Test folders were merged and re-split, because the images were collected from the web (the package lists the source URL of every image) and the same picture can appear in more than one folder.

Near-duplicates with conflicting labels — both removed after manual review (25 pairs)−50
Images retained for the experiments24,982

All retained images are RGB (24,854 JPEG, 119 PNG, 7 MPO, 2 BMP). The proposal's provisional total of 25,025 differs because the duplicate review was not complete at that time; every exclusion is recorded with its reason in assignment2/data/manifests/audit.csv.

Near-Duplicate Detection and Review

  1. Candidates: a 64-bit difference hash (dHash) of every image; pairs with Hamming distance ≤ 8 are candidates (1,718 pairs).
  2. Confirmation: the mean absolute difference of 32 × 32 grayscale thumbnails must be ≤ 30 (on a 0–255 scale). With dHash alone, different dishes with a similar layout (a round plate in the centre) were chained into groups of more than 250 images; the second check reduced the largest group to 9 images.
  3. Grouping: 480 confirmed same-label pairs form 412 duplicate groups. All images of a group are placed in the same split.
  4. Manual review: 54 confirmed pairs had different labels. 25 were the same picture filed under two dishes, so both images were removed; 29 were different dishes and both were kept as separate images.

Final Data Split

Split unit: duplicate group. For each class, its groups are shuffled with seed = 42 and assigned to test until about 15% of the class is reached, then to validation (about 15%); the remaining groups form the training set.

Class Imbalance and Input Sizes

The largest class (Bun bo Hue, 1,530 original images) is 3.45 times the smallest (Banh pia, 444). Macro-F1 is used as the primary metric so that every class has equal weight. Image sizes vary widely: median 1,000 × 720 pixels, widths 100–7,360 and heights 83–5,616 pixels. 346 retained images have a short side below 224 pixels and are upscaled by the resize step.

Preprocessing

Validation / testResize(232), CenterCrop(224) — the evaluation preprocessing of TorchVision ResNet50_Weights.IMAGENET1K_V2

Normalization uses the constants published with the pretrained weights; no statistic is computed from validation or test data. The same transforms are used for every model. A batch is a tensor of shape [B, 3, 224, 224] with integer labels 0–29.

Bias and Limitations of the Data

  • Images were collected from the web: many are stock or recipe photos with clean backgrounds, which may not represent everyday photos of food.
  • Several dishes look alike (e.g. Banh duc and Banh gio, Bun rieu and Bun mam), and the label-conflict review shows that some web images are filed under the wrong dish; further label noise may remain.
  • The duplicate check does not detect heavily cropped, rotated or re-photographed copies, and only label-conflicting pairs were reviewed by hand, so some leakage risk remains.

Methodology

Task and model outputs

Predict one of 30 Vietnamese food labels from an RGB image. Each model receives tensors shaped [B, 3, 224, 224] and returns 30 raw logits. Cross-entropy is applied directly to the logits; the largest logit determines the predicted class.

Scratch CNN baseline

The group-implemented CNN has 33 convolutional layers with BatchNorm and ReLU, spatial downsampling, global average pooling, and a two-layer classification head. All weights start from random initialization. This is a substantial scratch baseline; it has 21,249,886 trainable parameters.

Pretrained ResNet-50

TorchVision ResNet-50 uses ResNet50_Weights.IMAGENET1K_V2. Its original output layer is replaced by a linear head mapping 2,048 features to 30 logits. For M2, the backbone is frozen and only the new head is optimized. Backbone BatchNorm running statistics remain fixed, including when the training loop switches the model to training mode.

Preprocessing and pipeline

Reviewed manifests → RGB image loading → preprocessing → DataLoader → model → cross-entropy → Adam update → validation → checkpoint selection

Training uses RandomResizedCrop to 224 × 224 (scale 0.7–1.0), random horizontal flipping, and brightness/contrast/saturation jitter of 0.2. Validation resizes the shorter side to 232 pixels and center-crops to 224 × 224. Both models use ImageNet mean (0.485, 0.456, 0.406) and standard deviation (0.229, 0.224, 0.225). These fixed constants are not fitted on validation or test images.

The group provides the scratch architecture and orchestration code. ResNet-50, transforms, optimizers and tensor operations come from PyTorch/TorchVision; metric calculations use scikit-learn. The planned M3 controlled study compares the same pretrained ResNet-50 with a frozen backbone versus full fine-tuning.

Comparison & Discussion

Frozen ResNet-50 reached validation Accuracy of 72.45% and Macro-F1 of 0.7231, compared with 25.10% and 0.2005 for the scratch CNN. The differences are 47.35 percentage points in Accuracy and 0.5227 in Macro-F1.

The CNN improved through much of training but had fluctuating validation metrics, including a large validation-loss spike at epoch 2; its best validation Macro-F1 occurred at epoch 19. Frozen ResNet-50 improved more smoothly and reached its highest validation Macro-F1 at epoch 20. A fixed 20-epoch budget does not establish that either model has fully converged.

Only 61,470 head parameters were trainable in the frozen model, but the full backbone still computed image features. The measured epoch-loop times were similar: 2,715.15 seconds for the CNN and 2,744.06 seconds for ResNet-50. These totals do not identify a particular performance bottleneck; profiling is deferred until after M2.

Interpretation: the pretrained frozen configuration performs better in these runs. Architecture, initialization and learning rate changed together, so the gain cannot be attributed to one factor in isolation. M3 will compare frozen and fully trainable ResNet-50 while keeping the other factors fixed.

Limitations & Conclusion

  • Results cover one seed, one custom group-aware split and a fixed 20-epoch budget; run-to-run uncertainty has not been measured.
  • The scratch CNN has 33 convolutional layers and 21.25 million trainable parameters. Its continuing improvement suggests that a weak 20-epoch result is not evidence that every scratch CNN is unsuitable.
  • Web-photo bias, residual label noise and undetected transformed duplicates may affect generalization. The audit reduces known leakage but cannot guarantee its absence.
  • The held-out test set remains unused. Full fine-tuning, the controlled study, early-stopping extension, throughput profiling, inference-cost measurements and detailed qualitative error analysis are pending.

M2 conclusion: a reproducible pipeline, audited EDA, a completed scratch baseline and a completed pretrained frozen-backbone run are available. The selected frozen model reaches validation Macro-F1 0.7231. This is preliminary validation evidence; final generalization claims await the M3 study and locked-model test evaluation.

Checkpoint Access and Reproduction

The recorded checkpoints are stored locally in their run directories and excluded from Git. No checkpoint-download URL has been published. The following instructions describe how to reconstruct new runs; regenerated numerical results may vary across environments.

  1. Obtain the repository source and Kaggle version 11 images. Preserve paths under assignment2/data/raw/archive/Images/, then use the committed manifests rather than regenerating the split.
  2. For a reported run, commit the source/configuration and build the Docker image from those files. The current run records identify training source commit 5d106abab40a6720ebc5874b9a748f01356c965c; later comparison/plotting scripts are packaging additions.
  3. Run the commands below from assignment2/. Copy the new printed run IDs when verifying reproduced runs; the existing M2 run IDs are not automatically recreated.
$trainingCommit = git rev-parse HEAD
docker compose build

docker compose -f compose.yaml -f compose.gpu.yaml run --rm assignment2 python -m experiments.run --config config/baseline_cnn.yaml --epochs 20 --code_commit $trainingCommit

docker compose -f compose.yaml -f compose.gpu.yaml run --rm assignment2 python -m experiments.run --config config/resnet50.yaml --experiment-config config/ablation_frozen.yaml --epochs 20 --code_commit $trainingCommit

GPU execution requires compatible NVIDIA hardware/drivers and configured Docker GPU access (WSL 2 backend on Windows). Each command saves configuration, metadata, the best validation checkpoint, history and timing. Use python -m experiments.verify_checkpoint --run-dir RUN_DIRECTORY inside the same Docker GPU service to check a saved run. This reloads saved settings and evaluates validation only.
